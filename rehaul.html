Fine-Tuning Demos Rehaul Proposal

A customer-centered plan for turning the current collection of Microsoft Foundry fine-tuning demos into a coherent cookbook that grows from first principles to production-grade and agentic training.

Prepared 2026-10-03 | Scope: 16 demo areas, 20 canonical learning notebooks, shared navigation, metadata, standards, and migration plan

Recommendation Current gaps Architecture Learning path Demo catalog Notebook roles Standards Migration Reviewer feedback

Executive recommendation

Use a hybrid design: a maturity-first learning path for sequential study, task-oriented lookup for customers who know what they need, and technique/modality filters backed by machine-readable metadata. Do not immediately move every existing folder; preserve current URLs while the new curriculum proves itself.

Primary journey

Platform readiness → evaluation contract → first SFT → repeatable experimentation → DPO/RFT/distillation/multimodal → agentic workflows → release and operations.

Direct lookup

Let customers filter by task, technique, modality, notebook role, model family, maturity, access level, cost, and production readiness.

Stable public surface

Keep current folders as compatibility entry points during migration. Add canonical metadata and navigation before disruptive renaming.

Model-launch readiness

Keep conceptual guidance model-agnostic. Put changing model, region, quota, and feature support in a dated compatibility matrix.

What success looks like

  • A beginner can complete one small, measurable SFT job without hidden prerequisites.
  • An experienced customer can jump directly to DPO, RFT, multimodal, distillation, or tool-use examples.
  • Every notebook clearly states whether it trains a model, only evaluates, benchmarks, generates data, or supports another workflow.
  • Every result separates platform success, model-quality success, deployment success, and production readiness.
  • Every demo follows one documentation and notebook contract while retaining enough local code to remain understandable.

Current-state diagnosis

Mixed organizing dimensions

Technique, modality, scenario, and maturity are encoded together in folder names. Examples: SFT and RFT folders sit beside evaluation-only notebooks, vision workloads, and an integrated retail-agent capstone.

No dependable prerequisite path

The catalog suggests difficulty, but operational prerequisites vary much more: preview access, quota, many deployments, App Insights, hosted agents, functions, and tool endpoints.

Notebook responsibilities are unclear

Some notebooks train; others evaluate or benchmark; several combine data generation, training, deployment, and evaluation in one long stateful flow.

Inconsistent model roles

Base, teacher, evaluator, grader, inference-only, and fine-tuned models are often described together. Customers cannot reliably tell which model was actually optimized.

Production maturity stops early

Job submission and deployment are well represented. Shared patterns for data lineage, release gates, load testing, canary, rollback, monitoring, drift, and retirement are missing.

Catalog drift

The root documentation says 15 demos while the current inventory has 16 demo areas. Names, README coverage, notebook names, result claims, and model references have drifted.

Key pedagogical risk: a technically successful job can still produce a worse model, fail managed postprocessing, be undeployable because of quota, or be unsafe for production. The cookbook must teach these as distinct outcomes.

Naming policy

  • Use lowercase kebab-case for new machine-readable slugs: sft-bug-detection, rft-countdown, vision-chart-reasoning.
  • Use human-readable titles from metadata; do not force display names into folder names.
  • Use numbered notebook names that state the action: 01_prepare_data.ipynb, 02_train.ipynb, 03_evaluate.ipynb.
  • Never present or commit *.executed.ipynb as a separate cookbook. Publish execution evidence outside the customer source tree when needed.
  • Use one environment-variable prefix, preferably FOUNDRY_*.

Recommended sequential learning path

This is the primary path customers should see. Optional branches are clearly marked; not all 16 demos are prerequisites.

00

Platform readiness and orientation NO TRAINING

New module: project endpoint, Entra ID, permissions, supported model/region check, quota, budget, data residency, cleanup policy, and the seven-step fine-tuning lifecycle.

Exit gate: authentication succeeds, the target training type is supported, estimated cost is understood, and the learner can distinguish a base model, deployment, job, and fine-tuned model.

01

Evaluation contract and baseline NO TRAINING

New shared lesson: define train/validation/test splits, primary metric, regression suite, safety checks, minimum improvement threshold, and no-ship criteria before training.

The existing image/audio Evaluation notebooks become optional multimodal examples, not the sole introduction to evaluation.

Exit gate: a versioned baseline result and explicit success threshold exist.

02

First supervised fine-tuning job CORE TRAINING

Use: a simplified SFT_Bug_Detection. Split into baseline/data inspection, training/monitoring, and evaluation/decision. Make GPT-5.4 teacher generation and ROI analysis optional extensions.

Reinforce with: SFT_CNN_DailyMail. Offer SFT_PubMed_Summarization as a domain-risk branch.

Exit gate: the learner submits a small SFT job, compares base and fine-tuned models on identical held-out data, records cost/runtime, and cleans up temporary resources.

03

Dataset quality and repeatable experiments PRACTITIONER

New modules: schema validation, duplicate detection, contamination checks, coverage, token statistics, PII/secrets scanning, licensing, dataset manifests, experiment hypotheses, cost controls, and leaderboards.

Exit gate: every job is linked to a dataset hash/version, hypothesis, hyperparameters, SDK version, metrics, and decision.

04

Multimodal specialization OPTIONAL BRANCH

Order: chart reasoning → image breed classification → latency benchmarking → video action recognition. Audio/image evaluation remains an evaluation-only branch.

Exit gate: customers can version preprocessing, prevent split leakage, report per-class quality, and include latency/cost rather than quality alone.

05

Advanced optimization methods ADVANCED

Order: DPO preference optimization → RFT Countdown with deterministic/model graders → advanced math RFT. Advanced training is chosen only after SFT plus evaluation is shown insufficient.

Exit gate: the learner can justify the technique, validate the grader or preference data, preserve a simpler baseline, and distinguish training success from managed postprocessing and deployment success.

06

Synthetic data and distillation ADVANCED

Order: teacher-student basics with DistillingSarcasm → code distillation → schema-driven synthetic tool-use data → production trace distillation.

Separate data generation/acquisition from training so customers can inspect, filter, and approve data before incurring training cost.

Exit gate: teacher, student, baseline, evaluator, lineage, filtering, and contamination checks are explicit.

07

Tool use and agentic training ADVANCED / PREVIEW

Order: tool contracts and simulators → tool-use SFT → traces-to-SFT → deterministic agentic RFT → endpoint graders → retail-agent capstone.

Agentic_RFT_PrivatePreview remains clearly isolated as availability-dependent material. ZavaRetailAgent becomes the integration capstone, not an introductory tutorial.

Exit gate: tool schemas, side effects, retries, endpoint authentication, grader load, rollout termination, policy, and observability are versioned and tested.

08

Staging, release, operations, and lifecycle PRODUCTION

New modules: staging deployment, smoke/load tests, p50/p95 latency, cost SLOs, safety gates, canary/shadow evaluation, approval, rollback, monitoring, drift, retraining triggers, incident response, and retirement.

Exit gate: promotion is reversible, rollback is tested, the previous champion remains deployable, and operational alerts have owners.

Common standards for every cookbook

README contract

  1. One-sentence customer outcome.
  2. At-a-glance metadata: stage, technique, modality, notebook roles, stability, runtime, approximate cost, access and quota.
  3. What the customer will learn and when to use the technique.
  4. Prerequisites, permissions, regions/models, existing resources, and environment variables.
  5. Notebook map with a fine-tuning yes/no flag for each notebook.
  6. Dataset source, license, lineage, schema, counts, hashes, split strategy, and safety considerations.
  7. Expected outputs and explicit quality acceptance criteria.
  8. Restart-safe rerun behavior and how to reuse an existing successful job.
  9. Cleanup, troubleshooting, known service limitations, and preview status.
  10. Production considerations: safety, latency, cost, monitoring, rollback, and human review.

Notebook contract

0. Purpose, role badge, cost warning, and configuration
1. Authenticate and connect to the Foundry project
2. Validate prerequisites, model support, quota, and data
3. Establish a base-model baseline
4. Prepare and validate training/validation data
5. Upload or reuse files
6. Create or reuse the fine-tuning job
7. Monitor to a terminal state with explicit error handling
8. Deploy or invoke the resulting model
9. Evaluate against the same baseline contract
10. Record quality, safety, cost, latency, provenance, and decision
11. Cleanup and next steps

Every paid cell should say: "This cell submits a billable Foundry job. Check for an existing successful job before rerunning."

Shared components worth standardizing

Project context

DefaultAzureCredential, AIProjectClient, endpoint validation, model/deployment discovery, and actionable access errors.

Dataset validation

Schema, role order, lengths, duplicates, contamination, coverage, PII/secrets, hashes, source/license, and split manifest.

Evaluation harness

Base versus fine-tuned comparison, task graders, safety/regression suites, cost/latency capture, human-review sample, and JSON output.

Experiment manifest

Hypothesis, dataset/code versions, model, hyperparameters, job/model/deployment IDs, cost, metrics, decision, and approver.

Release helper

Candidate naming, staging, smoke/load test hooks, promotion, rollback, and cleanup.

Diagnostics index

User error, operation ID, service/log source, likely cause, query/command, remediation, and safe-retry guidance.

Shared helpers should stay small, tested, and transparent. Do not replace understandable notebook code with an opaque repository framework merely to remove duplication.

Technical guardrails

Data

  • Validate every JSONL row and role order before upload.
  • Keep train, validation, final test, safety, and operational replay sets distinct.
  • Record source, license, generation model/prompt, transforms, filters, random seed, and hashes.
  • Never treat synthetic or trace data as trusted without sampling and evaluation.

Graders and RFT

  • Prefer deterministic graders where possible.
  • Test positive, partial, malformed, adversarial, and reward-hacking cases.
  • Calibrate against base rollout distributions.
  • Keep training reward separate from independent final evaluation.

Evaluation

  • Compare base, fine-tuned, teacher/reference, and same-base peer where relevant.
  • Report sample counts, per-category results, confidence where practical, latency, token use, and cost.
  • Treat tiny perfect scores as instructional, not proof of generalization.
  • Include safety, refusal, format, and unrelated-capability regression suites.

Agentic workflows

  • Use deterministic tool simulators for introductory material.
  • Make side effects impossible or reversible during training.
  • Version tools, schemas, prompts, grader endpoints, and agent versions.
  • Measure retries, errors, latency, invalid arguments, race conditions, and termination reasons.

Multimodal

  • Declare modality/model compatibility and preprocessing version.
  • Prevent source, speaker, image, or clip leakage across splits.
  • Report robustness to crops, resolution, frame sampling, audio quality, and OCR variation.
  • Surface safety filtering and rejected-row counts.

Launch hygiene

  • Keep model/region/version claims in a dated compatibility matrix.
  • Record SDK/API version, region, tier, quota state, and result timestamp.
  • Separate platform failure from model-quality failure.
  • Secret-scan source, notebooks, and generated outputs before publication.

Phased migration plan

Phase 1 - Inventory and truth

Priority: P0

  • Correct counts and stale links.
  • Create _catalog.yml.
  • Classify all notebooks and model roles.
  • Add status, availability, cost, runtime, and known-limitations metadata.
  • Add catalog and link validation to CI.

Phase 2 - Navigation

Priority: P0

  • Add learning path, task index, and model/notebook index.
  • Generate catalog tables from metadata.
  • Keep existing folder URLs unchanged.
  • Add compatibility matrix for model/region/feature support.

Phase 3 - Foundations first

Priority: P0/P1

  • Create platform-readiness and evaluation-contract modules.
  • Refactor Bug Detection into the first safe SFT path.
  • Standardize CNN/DailyMail, PubMed, and Evaluation.
  • Add cost, rerun, cleanup, and no-ship guidance.

Phase 4 - Technique modules

Priority: P1

  • Refactor DPO/RFT and grader lessons.
  • Split data generation/acquisition from training.
  • Normalize multimodal preprocessing and evaluation.
  • Add dataset and experiment manifests.

Phase 5 - Release and operations

Priority: P2

  • Add staging, smoke/load tests, safety gates, and canary/shadow patterns.
  • Add tested promotion and rollback.
  • Add monitoring, drift, retraining, incident, and retirement modules.

Phase 6 - Optional physical moves

Priority: P3

  • Adopt new slugs for new content first.
  • Move legacy folders only with compatibility stubs.
  • Update internal and external references.
  • Deprecate old paths before removal.

Migration acceptance criteria

  • Catalog count equals repository inventory and CI enforces it.
  • Every canonical notebook has exactly one role label and a fine-tuning yes/no field.
  • Every training demo identifies exact or runtime-configured base and output model roles.
  • Every demo has entry/exit objectives, cost/runtime expectations, cleanup, and known limitations.
  • Every advanced module declares prerequisite gates.
  • Every checked-in result is reproducible from sanitized metadata and does not contain credentials.
  • At least one complete path exists from readiness through tested rollback.

Consensus: the highest-value near-term work is not adding more demos. It is separating learning objectives, making evaluation and model roles explicit, standardizing the cookbook contract, and adding the missing bridge from successful experiment to safely operated model.

Recommended decision

  1. Approve the hybrid information architecture and metadata-first migration.
  2. Do not immediately rename or move all current folders. First add catalog metadata, navigation, role labels, and CI validation.
  3. Build the foundation path first: readiness, evaluation contract, simplified Bug Detection SFT, and repeatable experiment artifacts.
  4. Then refactor by learning dependency: DPO/RFT, multimodal, synthetic/distillation, and finally agentic capstones.
  5. Commit to production completeness: add staging, load/safety gates, canary, tested rollback, monitoring, and lifecycle modules as first-class cookbooks.
Proposal based on direct repository inventory and four parallel customer-perspective reviews. This document is a reorganization plan; it does not move or rename the current demos.
