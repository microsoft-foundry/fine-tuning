Fine-Tuning Demos Rehaul Proposal

A customer-centered plan for turning the current collection of Microsoft Foundry fine-tuning demos into a coherent cookbook that grows from first principles to advanced multimodal, reasoning, distillation, and agentic training.

Prepared 2026-10-03 | Scope: 16 demo areas reviewed, 14 proposed curriculum demos, 4 skipped notebooks, clean-slate structure, metadata, standards, and implementation plan

Recommendation Current gaps Architecture Learning path Demo catalog Notebook roles Skipped notebooks Standards Implementation Reviewer feedback

Executive recommendation

Use a clean-slate hybrid design: physically organize the new location by customer maturity, provide task-oriented lookup for customers who know what they need, and use machine-readable metadata for technique, modality, model, and capability filters.

Primary journey

Foundations → core SFT → multimodal SFT → core RFT → agentic RFT → data and distillation.

Direct lookup

Let customers filter by task, technique, modality, notebook role, model family, maturity, access level, cost, and expected runtime.

Clean canonical structure

Apply the new hierarchy, slugs, notebook names, and common contracts directly in the new destination.

Model-launch readiness

Keep conceptual guidance model-agnostic. Put changing model, region, quota, and feature support in a dated compatibility matrix.

What success looks like

  • A beginner can complete one small, measurable SFT job without hidden prerequisites.
  • An experienced customer can jump directly to RFT, multimodal, distillation, or agentic examples.
  • Every notebook clearly states whether it trains a model, only evaluates, benchmarks, generates data, or supports another workflow.
  • Every result separates platform success, model-quality success, and deployment success.
  • Every demo follows one documentation and notebook contract while retaining enough local code to remain understandable.
  • Every demo is portable: no committed file contains a specific Foundry resource, project endpoint, region default, API key, subscription, tenant, deployment, or customer identifier.
  • Every demo preserves its current training, validation, and holdout datasets byte-for-byte; the rehaul changes organization and presentation, not experiment data.

Current-state diagnosis

Mixed organizing dimensions

Technique, modality, scenario, and maturity are encoded together in folder names. Examples: SFT and RFT folders sit beside evaluation-only notebooks, vision workloads, and an integrated retail-agent capstone.

No dependable prerequisite path

The catalog suggests difficulty, but operational prerequisites vary much more: preview access, quota, many deployments, App Insights, hosted agents, functions, and tool endpoints.

Notebook responsibilities are unclear

Some notebooks train while others evaluate or benchmark, and related steps are distributed inconsistently. Customers cannot reliably tell which single notebook represents the complete prepare, train, and evaluate journey for a demo.

Inconsistent model roles

Base, teacher, evaluator, grader, inference-only, and fine-tuned models are often described together. Customers cannot reliably tell which model was actually optimized.

Learning contracts are inconsistent

Entry requirements, expected outputs, evaluation criteria, cost warnings, rerun behavior, cleanup, and known limitations vary significantly across demos.

Catalog drift

The root documentation says 15 demos while the current inventory has 16 demo areas. Names, README coverage, notebook names, result claims, and model references have drifted.

Key pedagogical risk: a technically successful job can still produce a worse model, fail managed postprocessing, be undeployable because of quota, or be unsafe for production. The cookbook must teach these as distinct outcomes.

Resolved implementation decisions

  • Destination: build the clean-slate structure under repository-root cookbooks/. The current Demos/ tree remains the migration source until the new curriculum is validated.
  • Foundations: 00-platform-readiness and 01-evaluation-contract are documentation modules, not additional demos or standalone notebooks. Their checks and evaluation pattern are exercised in the first Bug Detection notebook.
  • Image latency: merge latency benchmarking into the image-classification demo.ipynb; it is not an approved second notebook.
  • Training data source: the notebook must train on the data produced by the preparation path it visibly demonstrates. If it fetches, generates, or acquires data live, that resulting validated dataset is the training input. Use preserved existing inputs only for demos whose canonical workflow does not produce the data live. Never download or generate one dataset and silently train on another.
  • Skipped content: do not copy DPO, endpoint-grader, image-evaluation, or audio-evaluation notebooks into the new customer location. They remain only in the source tree as non-curriculum reference/history.
  • Dependencies: use one central pinned Python environment. Do not create independently drifting per-demo requirements files.
  • Runtime identifiers: resource, region, job, model-result, deployment, and operation identifiers may appear only in ignored outputs/ from the user's current run. Committed notebooks, metadata, and assets remain identifier-free.
One-notebook default: each demo should have one canonical demo.ipynb that keeps data preparation, baseline measurement, fine-tuning, monitoring, deployment or invocation, and evaluation together. Split a demo only when a genuine platform boundary makes one notebook impractical, and document that exception in demo.yaml and the README. Complexity alone is not sufficient reason to split the customer journey.
Customer-facing evidence policy: every notebook should include sanitized charts, pictures, tables, and headline numbers from a representative completed existing run so customers can understand the expected outcome without launching a paid job. Evidence must remain honest when a run completed but quality regressed or another outcome was unfavorable. Keep these compact, checked-in teaching artifacts under assets/charts/, assets/images/, and assets/metrics/, then render them inline at the relevant notebook step. Add the footnote "Actual results may vary by model version, data, configuration, region availability, and service conditions." Runtime output from the customer's own execution belongs under ignored outputs/. Internal refactor reports, raw execution snapshots, report-generator inputs, credentials, resource-specific URLs, and aggregate tracking HTML must not ship.
Dataset preservation invariant: do not alter, regenerate, resample, relabel, rebalance, filter, or replace any existing committed training, validation, or holdout dataset during the rehaul. Move files only as needed for the new structure, preserve their contents and split membership exactly, and verify hashes before and after migration. For workflows that fetch, generate, or acquire data live, preserve the current preparation logic and train on its validated runtime output rather than substituting a committed snapshot.

Naming policy

  • Use lowercase kebab-case for new machine-readable slugs: sft-bug-detection, rft-countdown, vision-chart-reasoning.
  • Use human-readable titles from metadata; do not force display names into folder names.
  • Use demo.ipynb as the canonical notebook name and organize it with numbered sections for prepare, baseline, train, monitor, deploy/invoke, and evaluate.
  • If a split is absolutely necessary, use the smallest possible number of action-oriented notebooks and record the reason and execution order in metadata.
  • Never present or commit *.executed.ipynb as a separate cookbook. Publish execution evidence outside the customer source tree when needed.
  • Use one environment-variable prefix, preferably FOUNDRY_*.
  • Use consistent snake_case for Python variables/functions and generated filenames, PascalCase for classes, and lowercase kebab-case for demo folders and resource display-name components.
  • Name uploaded files, jobs, deployments, evaluation runs, manifests, charts, and metrics for the demo and purpose, such as news-summarization-train.jsonl and news-summarization-sft; avoid generic names such as train.jsonl, job, or deployment1.
  • Use the same terminology, heading sequence, status language, and result-summary shape across demos without removing scenario-specific explanations or technical depth.

Recommended sequential learning path

This is the primary path customers should see. It contains six ordered tracks; optional and skipped notebooks are documented separately.

00

Foundations ORIENTATION + FIRST SFT

Modules: platform readiness, evaluation contract, and a simplified SFT_Bug_Detection first job.

Teach project endpoint and Entra ID, model/region support, quota, cost awareness, train/validation/test separation, baseline measurement, file processing, job submission, and base-versus-fine-tuned comparison.

Exit gate: the learner can authenticate, validate the data, submit one small SFT job, identify the resulting model, and demonstrate improvement against a declared baseline.

01

Core SFT CORE TRAINING

Order: news summarization → scientific summarization. Reuse the foundation workflow while changing data shape, domain, evaluation metric, and risk profile.

Standardize schema validation, duplicates, contamination checks, coverage, token statistics, PII/secrets scanning, licensing, dataset manifests, and structured experiment summaries.

Exit gate: the learner can adapt the SFT workflow to a new text task and explain why the evaluation method must change with the task.

02

Multimodal SFT OPTIONAL BRANCH

Order: chart reasoning → image breed classification with integrated latency benchmarking → video action recognition.

Exit gate: customers can version preprocessing, prevent split leakage, report per-class quality, and include latency/cost rather than quality alone.

03

Core RFT ADVANCED

Order: RFT Countdown with model/score and Python grader variants → advanced math RFT.

Teach reward design, grader calibration, deterministic validation, reward-hacking checks, training progress, and the difference between training, evaluation, and deployment outcomes.

Exit gate: the learner can validate a grader independently, justify RFT for the task, submit an RFT job, and evaluate the result with a separate test contract.

04

Agentic RFT ADVANCED / PREVIEW

Order: agentic RFT with tool calls → retail-agent capstone.

Agentic_RFT_PrivatePreview remains clearly isolated as availability-dependent material. ZavaRetailAgent becomes the integration capstone, not an introductory tutorial.

Exit gate: tool schemas, tool authentication, grader contracts, failure behavior, rollout termination, policy constraints, and evaluation are explicit and reproducible.

05

Data and distillation ADVANCED

Order: teacher-student basics with DistillingSarcasm → code distillation → schema-driven synthetic tool-use data → agent trace distillation.

Keep generation or acquisition, inspection, filtering, approval, training, and evaluation as clearly separated sections within one canonical notebook so customers can review data before incurring training cost without losing the end-to-end narrative.

Exit gate: teacher, student, baseline, evaluator, data provenance, filtering, and contamination checks are explicit.

Common standards for every cookbook

README contract

  1. One-sentence customer outcome.
  2. At-a-glance metadata: stage, technique, modality, notebook roles, stability, runtime, approximate cost, access and quota.
  3. What the customer will learn and when to use the technique.
  4. Prerequisites, permissions, supported model requirements, and environment variables without naming a specific customer resource or default region.
  5. Canonical notebook link and a fine-tuning yes/no flag; document any rare multi-notebook exception and its required order.
  6. Dataset source, license, provenance, schema, counts, hashes, split strategy, and safety considerations.
  7. Expected outputs and explicit quality acceptance criteria.
  8. Restart-safe rerun behavior and how to reuse an existing successful job.
  9. Cleanup, troubleshooting, known service limitations, and preview status.
  10. Real-world adaptation considerations: safety, latency, cost, privacy, and human review.
  11. A final summary of fine-tuning gains, key lessons, caveats, and the next notebook in the sequential curriculum.

Configuration and secret contract

  • Remove committed references to specific Foundry resources, project endpoints, regions, subscriptions, tenants, deployment names, job URLs, API keys, and customer identifiers from notebooks, scripts, READMEs, metadata, assets, and sample output.
  • Use a committed .env.template containing variable names and descriptions only. Users copy it to ignored .env and provide their own project endpoint, supported region or project context, model/deployment choices, and optional runtime parameters.
  • Do not place a working endpoint, region, resource name, deployment name, credential, or apparently usable placeholder in notebook defaults. Fail fast with a clear list of missing variables.
  • Prefer Entra ID and DefaultAzureCredential. If a feature genuinely requires a key, read it only from the user's environment, never print it, and never include it in committed examples or output.
  • Resolve all configuration once near the start of the notebook through a shared typed/validated helper; later cells consume the validated configuration object rather than repeatedly reading environment variables.
  • Committed teaching assets remain identifier-free. The user's current region, resource, job, model-result, deployment, and operation IDs may be recorded only in ignored runtime manifests under outputs/.

Notebook contract

Use one canonical demo.ipynb per demo. The notebook must be understandable in read-only mode: before any billable or long-running step, show compact inline evidence from a representative existing run, including the most useful charts, pictures, tables, job duration/status, sample counts, quality metrics, loss or reward curves where available, and base-versus-fine-tuned comparison. Clearly label saved evidence with its model, dataset version, and execution date so it is not mistaken for the reader's live output; remove resource-specific URLs and identifiers from committed evidence.

0. Purpose, role badge, cost warning, and configuration
1. Authenticate and connect to the Foundry project
2. Validate prerequisites, model support, quota, and data
3. Prepare, inspect, and validate training/validation data
4. Establish and visualize a base-model baseline
5. Upload or reuse files
6. Create or reuse the fine-tuning job
7. Monitor to a terminal state and show representative training evidence
8. Deploy or invoke the resulting model
9. Evaluate against the same baseline contract with charts, examples, and numbers
10. Summarize fine-tuning gains: loss/reward curves, evaluation deltas, safety, cost, latency, and decision
11. State key learning, limitations, and the next notebook in the curriculum
12. Cleanup

Every representative chart, image, table, and metric should load from the local assets/ folder so the notebook remains useful without execution. End the evidence section with: "Actual results may vary by model version, data, configuration, region availability, and service conditions."

Shared components worth standardizing

Project context

DefaultAzureCredential, AIProjectClient, endpoint validation, model/deployment discovery, and actionable access errors.

Configuration

One validated .env loader, required-variable checks, redacted diagnostics, typed values, and no resource- or region-specific committed defaults.

Dataset validation

Schema, role order, lengths, duplicates, contamination, coverage, PII/secrets, hashes, source/license, and split manifest.

Evaluation harness

Base versus fine-tuned comparison, task graders, safety/regression suites, cost/latency capture, human-review sample, and JSON output.

Experiment manifest

Hypothesis, dataset/code versions, model, hyperparameters, job/model/deployment IDs, cost, metrics, and decision. Identifier-bearing manifests are runtime artifacts under ignored outputs/; committed metadata contains only sanitized teaching evidence.

Notebook scaffolding

One end-to-end notebook with consistent configuration, preflight checks, preparation, baseline, job reuse, training, inline representative-run visuals, evaluation, structured result summaries, cleanup, and clear next-step guidance.

Foundry operations

Uniform, meaningful helpers for file upload/reuse, job creation/monitoring, deployment/invocation, and evaluation creation/polling. Names derive from the demo slug and purpose, and every operation returns a consistent structured result.

Reliability and logging

Consistent customer-readable logs, bounded retries with backoff only for transient failures, timeouts, terminal-state handling, operation IDs, and actionable errors without swallowing failures or leaking secrets.

Diagnostics index

User error, operation ID, service/log source, likely cause, query/command, remediation, and safe-retry guidance.

Shared helpers should stay small, tested, and transparent. Do not replace understandable notebook code with an opaque repository framework merely to remove duplication.
Customer-facing code-quality rule: remove duplicated imports, dead branches, debug probes, one-off migration code, stale commented blocks, unused variables, unexplained constants, repeated polling loops, and redundant transformations. Keep only code that teaches the scenario or is required to run it, while preserving the technical explanations, edge cases, and domain depth already present.

Technical guardrails

Data

  • Validate every JSONL row and role order before upload.
  • Keep train, validation, final test, safety, and operational replay sets distinct.
  • Preserve all existing training, validation, and holdout file contents and split membership during migration; verify pre/post-move hashes.
  • Maintain explicit data lineage from the notebook's preparation output to the exact uploaded training/validation files. Live-fetched, generated, or acquired data must be the data trained on after validation; preserved inputs are used only when preparation is not live.
  • Record source, license, generation model/prompt, transforms, filters, random seed, and hashes.
  • Never treat synthetic or trace data as trusted without sampling and evaluation.

Graders and RFT

  • Prefer deterministic graders where possible.
  • Test positive, partial, malformed, adversarial, and reward-hacking cases.
  • Calibrate against base rollout distributions.
  • Keep training reward separate from independent final evaluation.

Evaluation

  • Compare base, fine-tuned, teacher/reference, and same-base peer where relevant.
  • Report sample counts, per-category results, confidence where practical, latency, token use, and cost.
  • Treat tiny perfect scores as instructional, not proof of generalization.
  • Include safety, refusal, format, and unrelated-capability regression suites.

Agentic workflows

  • Use deterministic tool simulators for introductory material.
  • Make side effects impossible or reversible during training.
  • Version tools, schemas, prompts, grader definitions, and agent versions.
  • Measure retries, errors, latency, invalid arguments, race conditions, and termination reasons.

Multimodal

  • Declare modality/model compatibility and preprocessing version.
  • Prevent source, speaker, image, or clip leakage across splits.
  • Report robustness to crops, resolution, frame sampling, audio quality, and OCR variation.
  • Surface safety filtering and rejected-row counts.

SDK and service calls

  • Use shared helpers and consistent return shapes for uploads, jobs, deployments, inference, and evaluations.
  • Retry only documented transient failures with bounded exponential backoff and jitter; never retry invalid input, authentication, quota, safety, or other terminal errors as if they succeeded.
  • Log operation names, states, elapsed time, and safe correlation IDs consistently; redact credentials, endpoints, and customer identifiers.
  • Use meaningful demo-derived remote names and local filenames so portal resources and downloaded artifacts remain understandable.

Launch hygiene

  • Keep model/region/version claims in a dated compatibility matrix.
  • Record SDK/API version, region, tier, quota state, and result timestamp only in the user's ignored runtime manifest; keep committed assets identifier-free.
  • Separate platform failure from model-quality failure.
  • Secret- and identifier-scan source, notebooks, assets, metadata, and generated outputs before publication.

  • Inventory every training, validation, and holdout file with its path, split role, size, and hash before moving anything.
  • Scan all demo files for committed resource names, endpoints, regions, deployment names, keys, identifiers, and inconsistent naming.
  • Define CI validation for metadata, notebooks, links, and secrets.

Phase 2 - Scaffold the new location

Priority: P0

  • Create the numbered physical hierarchy and shared folder.
  • Add the learning path, task index, and model/notebook index.
  • Generate all catalog tables and badges from metadata.
  • Add compatibility matrix for model/region/feature support.
  • Add shared configuration, logging, retry, naming, Foundry-operation, and error-handling helpers.
  • Create the common .env.template, notebook section template, conclusion template, and assets/ convention.
  • Create one central pinned environment; demos declare capability metadata rather than separate requirements files.

Priority: P0/P1

  • Create platform-readiness and evaluation-contract modules.
  • Rebuild Bug Detection as the first safe SFT path.
  • Rebuild news/scientific summarization with evaluation integrated into each canonical notebook under the common contract.
  • Remove redundant and migration-only code while preserving the explanatory depth and scenario-specific details.

Phase 4 - Build multimodal SFT and core RFT

Phase 6 - Quality gate and publish

Priority: P0 for launch

  • Run every canonical path from a clean environment.
  • Verify model-role, notebook-role, cost, cleanup, and availability metadata.
  • Run link, schema, notebook, accessibility, secret, resource-identifier, naming, and dataset-hash checks.

  • Publish the new location as one coherent cookbook.

Implementation acceptance criteria

  • Catalog count equals repository inventory and CI enforces it.
  • Every demo has exactly one canonical end-to-end notebook unless metadata records an approved platform-driven exception.
  • Every canonical notebook has exactly one role label and a fine-tuning yes/no field.
  • Every training demo identifies exact or runtime-configured base and output model roles.
  • Every demo has entry/exit objectives, cost/runtime expectations, cleanup, and known limitations.
  • Every advanced module declares prerequisite gates.
  • Every notebook renders sanitized charts, pictures, tables, and headline numbers from a representative existing run before asking the customer to execute paid steps.
  • Every checked-in result identifies its source model, dataset version, and execution date, includes the variability footnote, and contains no credentials, endpoints, regions, Foundry resource names, job URLs, or customer identifiers.
  • Every demo loads user-provided settings from ignored .env through a common validated configuration helper, with no specific resource or region default.
  • All demos resolve from the same centrally pinned Python environment; no per-demo dependency file can drift independently.
  • Every upload, job, deployment, evaluation, generated filename, variable, function, and script follows the shared naming convention and uses a meaningful demo-derived name.
  • Every service operation uses consistent logging, timeout, retry, terminal-state, and explicit error-handling behavior.
  • Every notebook concludes with fine-tuning gains, including loss/reward curves and evaluation deltas where available, key learning, limitations, and the next curriculum step.
  • All original training, validation, and holdout dataset hashes and split membership match the pre-rehaul inventory.
  • Every demo proves lineage from its visible preparation step to the exact uploaded files: live-fetched/generated/acquired data is trained on when produced, while preserved inputs are used only when the canonical workflow does not create data live.
  • Customer-facing notebooks and scripts contain no dead, redundant, migration-only, or unexplained code while retaining the original technical depth.
  • At least one complete path exists from readiness through an advanced agentic capstone.
